# W9 深化：进阶 RAG 也修不了？根因在切片粒度

> 接 W9 的「反直觉结果」，本周（深化）接入 Multi-Query + Rerank 做三方 A/B，看能否修复。
> **结论：没修复，但挖出了更深的根因——这比"修好了"更有价值。**

## 一、三方 A/B 结果（8 题）

| 指标 | 无RAG | 基础RAG(BGE top3) | 进阶RAG(MQ+Rerank) |
|---|---|---|---|
| 关键词命中率 | 75.0% | 62.5% | 58.3% |
| LLM 评委均分 | 10.0 | 7.9 | 8.1 |
| 编造率 | 0% | 12% | 12% |

关键题「递归函数必须具备哪两个要素？」：
- 无RAG → 评委 10 分
- 基础RAG → 评委 1 分，编造
- 进阶RAG → 评委 2 分，编造（**几乎没改善**）

## 二、根因升级：不是检索算法，是切片粒度

W9 我以为是「检索召回不完整」，于是上 Multi-Query + Rerank 加强检索。结果**没用**。

深挖发现真正的问题：教材 `递归.md` 按空行切成：

```
chunk0: "递归是函数「自己调用自己」的写法。任何递归都必须有两要素："
chunk1: "## 1. 终止条件（base case）..."       ← 答案在这里
chunk2: "## 2. 递推关系..."                     ← 答案在这里
```

问题问「哪两个要素」，语义上**最接近的是 chunk0（那句只说"有两要素"的废话）**，而真正的答案分散在 chunk1 + chunk2。

**无论 multi-query 生成多少变体、rerank 怎么精排，都改变不了"答案内容被切碎在多个 chunk 里"这个事实。**

## 三、真正的教训（RAG 的分层）

```
切片（chunking）  >  检索（retrieval）  >  生成（generation）
    地基             中层              上层
```

**切片是地基。地基歪了，上层再精密的检索算法也救不回来。**

这也解释了为什么「无 RAG」反而满分：DeepSeek 本身就会"递归两要素"，它不需要检索；而 RAG 把答案切碎后，检索拿不到完整答案，反而拖后腿。

## 四、真正的修复方向（不是堆算法）

1. **按标题/语义切片**：让「## 1. 终止条件」「## 2. 递推关系」各自成完整 chunk，而不是按空行切碎
2. **合并相邻 chunk**：chunk0 这种"引子"要和后面的内容合并
3. **测试集换领域知识**：测"模型不知道的内容"，RAG 价值才体现得出来

## 五、面试怎么讲这个故事（完整闭环）

> "我搭了评测体系，A/B 实验发现加了 RAG 反而更差。我先怀疑是检索召回问题，上了 Multi-Query + Rerank，结果没用。深挖发现根因在**切片粒度**——答案被切碎在多个 chunk 里，检索算法救不了。这让我理解了 RAG 的分层：**切片 > 检索 > 生成**，地基才是关键。"

**这比"我会用 LangChain 搭 RAG"强一百倍——因为它证明你真的理解 RAG 的内部机制，而不是调包。**

---

## 六、修复验证（改切片 → 反转 ✅）

把切片从「按空行」改成「按 markdown 标题」（每个 `##` 标题自成 chunk），重跑三方 A/B：

| 指标 | 无RAG | 基础RAG(改切片后) | 进阶RAG |
|---|---|---|---|
| LLM 评委均分 | 10.0 | **9.1** | 8.1 |
| 编造率 | 0% | **0%** | 12% |

关键题「递归两要素」：基础 RAG 评委 **1 分 → 10 分**，编造「是 → 否」✅

**结论坐实：切片是地基。** 地基修好（按标题切），基础 BGE top3 就够了；
反而 Multi-Query + Rerank 因召回过多引入噪声，退步了（评委 8.1、编造 12%）。

## 七、完整闭环（面试最强故事）

```
发现缺陷 → 试检索算法（MQ+Rerank）没用 → 定位切片根因 → 改切片修复 → 验证满分
  (1分)      (2分, 没修好)              (按标题切)          (10分)
```

这四步每一步都有真实数据，讲出来就是一份"真的做过 RAG 且懂内部机制"的证明。
